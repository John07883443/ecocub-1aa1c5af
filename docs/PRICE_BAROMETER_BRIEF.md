# Барометр цен Подмосковье — бриф для нового раздела «Аналитика»

Постановка от владельца (голосовые сообщения, 2026-08-16 ночь/утро), зафиксирована
здесь дословно по смыслу, чтобы не растерять контекст между сессиями.

## Что нужно (MVP, шаг 1)

1. Новый пункт главного меню **«Аналитика»**, внутри — **«Барометр цен Подмосковье»**
   (можно как один прямой пункт меню на MVP, без выпадающего подменю — решить по месту).
2. Отдельная страница со стилизованной, упрощённой интерактивной картой Московской
   области, разбитой на **направления** (не буквальная географическая карта — упрощённая,
   с основными трассами, в духе дашборда). Данные по направлениям и трассам —
   `content/analytics/price-barometer.json` (см. ниже), поле `directions`.
3. **Южное направление** — единственное активное на старте (пилот, посёлок River Park,
   Ступинский район). Остальные семь направлений видны на карте, но помечены
   **«в разработке»** (не кликабельны на статистику, просто задел на будущее — так и
   просил владелец, чтобы было понятно, что раздел будет расти).
4. Поведение карты: **hover** подсвечивает направление, **click** раскрывает список
   отслеживаемых посёлков/проектов в этом направлении и их базовую статистику
   (свободно / продано / забронировано на сегодня, по каждому застройщику/проекту).
5. Реестр отслеживаемых посёлков — тоже в JSON (`villages`). На MVP это один посёлок
   (River Park), но структура рассчитана на добавление новых без переделки компонента.
6. Показывать текущие акции/скидки по отслеживаемым посёлкам (`village.promotions`).

Владелец явно обозначил это как **итеративную MVP-first задачу**: «первый MVP этого
раздела, будем уточнять» — не нужно стремиться к финальной полировке сразу, но
раздел должен выглядеть цельно и презентабельно, не как черновик (его прямые слова:
«надо чтобы сам ты всё нашёл, разместил, чтобы красиво выглядело» — оформление и
подбор решений делегированы Claude).

## Откуда данные

`content/analytics/price-barometer.json` (этот репозиторий) — уже подготовлен
локальным агентом. Формат такой же по духу, как `content/projects/*.json`.
Дополнил обязательно только **агрегированные** цифры (медианы, счётчики по статусам,
диапазоны цен) — **никаких персональных данных** (ФИО владельцев участков,
кадастровые номера). Причина: сырой виджет-датасет с dgtime.ru отдаёт ФИО реального
покупателя по каждому проданному участку (проверено на примере участка владельца
V83 — в сыром JSON лежит его настоящее имя). Это приватные данные третьих лиц, им
не место в публичном репозитории и уж тем более на боевом сайте. Если в будущем
понадобится по-участочная детализация на сайте — выводить **только** id участка,
статус и цену, без поля `owner`, и брать её из отдельного публичного экспорта, а не
копипастой сырого файла.

Источник агрегатов — приватный репозиторий `ecocub-data`
(`ECOCUB\api_data\land_prices_riverpark.json` + растущий
`ECOCUB\api_data\land_prices_trend_riverpark.csv`), который ведёт локальный агент
на машине владельца по расписанию (ежедневно). Обновлять
`content/analytics/price-barometer.json` в этом репозитории на следующих итерациях
будет тоже локальный агент — либо коммитом сюда, либо (правильнее по архитектуре
проекта — см. `ECOCUB/CLAUDE.md`) через Supabase, чтобы обновление цифр не требовало
пересборки и передеплоя сайта при каждом изменении. На MVP статичного JSON достаточно.

## Важные ограничения по месту

- Смотри `CLAUDE.md` в корне репозитория (раздел про облачного/локального агента и
  про прямую ссылку на изменённый экран после деплоя) — обязательно к прочтению
  перед стартом, если попал в эту сессию впервые.
- Главное меню (`src/lib/site.ts`, `mainNav`) уже содержит 8 пунктов, и в `Header.tsx`
  есть явный комментарий, что на 1024–1280px строка меню и так еле помещается
  (`xl:flex`, не `lg:flex`, — сознательное решение). Девятый пункт может потребовать
  либо сокращения подписи («Аналитика» короче, чем «Барометр цен», подойдёт для
  самого пункта меню — подстраницу назвать длиннее), либо пересмотра брейкпоинта.
  Прежде чем добавлять пункт в `mainNav`, проверь, как это выглядит на 1280px.
- Публичные роуты уже существуют по паттерну `/technology`, `/portfolio` и т.д.
  (TanStack Router, файлы в `src/routes/`) — сделать новый роут в том же стиле,
  например `/analytics` или `/price-barometer` (имя финально выбрать самостоятельно,
  владелец не называл конкретный slug).
- После деплоя на боевой сайт — обязательно дать владельцу прямую ссылку на новый
  экран (стандартное правило проекта, см. `CLAUDE.md`).
- Эта работа велась на ветке `feature/price-barometer-analytics` (запушена, НЕ в
  `main` — деплой триггерится только пушем в `main`, см. `.github/workflows/deploy.yml`).
  Веди дальнейшую работу либо в этой ветке, либо смёржи её в свою — на усмотрение,
  главное не терять контекст брифа и уже подготовленный JSON.

## Явно НЕ входит в шаг 1 (по словам владельца — «будем уточнять» дальше)

- Остальные 8 направлений и остальные посёлки ZMO (Гринвуд, White Park, Green Forest
  Club и т.п.) — пилотом сознательно выбран только South/River Park.
- Историческая динамика цен на графике — пока накоплено меньше суток истории
  (сбор стартовал 2026-08-16 утром), полноценный график по времени будет иметь смысл
  показывать позже, когда накопится содержательный тренд.
- Публикация raw-данных на уровне отдельного участка на сайте — см. ограничение выше
  про персональные данные.
