# Журнал релизов и процедура отката

---

## Как устроен деплой

```
push в main → GitHub Actions (.github/workflows/deploy.yml)
            → SSH под пользователем deploy
            → /home/deploy/deploy.sh
            → git reset --hard origin/main
            → npm ci
            → NITRO_PRESET=node-server npm run build
            → pm2 reload ecocub
            → проверка HTTP 200 в течение 30 секунд
            → нет 200 → автоматический откат на предыдущую сборку
```

Лог на сервере: `/var/log/ecocub/deploy.log`. Полный цикл около полутора минут.

**Важно.** Отдельной команды «выложить» не существует. `deploy.sh` делает `git reset --hard origin/main`, поэтому **любой пуш в `main` — немедленный деплой в production.** Работа ведётся в ветке; слияние в `main` и есть боевой релиз.

Конфигурация nginx лежит в `/etc/nginx/sites-available/ecocub` — **вне репозитория**. Деплоем не доставляется, правится на сервере отдельно.

### Процедура отката

| Сценарий | Действие |
|---|---|
| Сборка не проходит на сервере | срабатывает сам `deploy.sh`: нет 200 за 30 с → предыдущая сборка |
| Релиз выложен, обнаружена проблема | `git revert` коммита слияния в `main` → автодеплой возвращает состояние |
| Нужен полный возврат | `git reset --hard e8fd5a7` в `main` и пуш (согласуется отдельно) |
| Проблема в nginx | восстановление из `/etc/nginx/sites-available/ecocub.bak.<дата>` → `nginx -t` → перезагрузка |

Точка `e8fd5a7` не удаляется до завершения пострелизной проверки.

### Пострелизная проверка

Выполняется из сети владельца через браузер, а не по отчёту:

1. коды ответа всех 29 адресов статей;
2. число `canonical` на трёх типах страниц;
3. число адресов в `sitemap.xml` и элементов в `rss.xml`;
4. 404 на несуществующем теге;
5. первый экран: «сборка на участке за 10 дней»;
6. отправка тестовой заявки, проверка, что источник дошёл в Telegram;
7. `deploy.log` без ошибок.

## Следующий шаг после релиза: редиректы `/tpost/`

**Выполняется только после того, как `/blog/<slug>` отдают 200 на production.** Иначе 301 приведёт в 404, что хуже нынешнего состояния.

**Подтверждённый факт, влияющий на процедуру.** В nginx сейчас действует временное правило `^~ /tpost/` → `/blog`. Префикс с `^~` в nginx **имеет приоритет над всеми регулярными выражениями**. Файл `deploy_redirects_tpost.conf` состоит из правил `location ~ ^/tpost/<uid>` — то есть регулярных.

Значит подключить его рядом с действующим правилом нельзя: **все 29 правил будут молча проигнорированы**, без ошибки и предупреждения.

Правильный порядок в одной правке:

1. резервная копия `/etc/nginx/sites-available/ecocub.bak.<дата>`;
2. удалить временное `^~ /tpost/`;
3. добавить 29 правил по uid и общий случай `location ~ ^/tpost/ { return 301 /blog; }` последним;
4. `nginx -t`;
5. перезагрузить nginx;
6. проверить пять адресов: код 301, конечный код 200, отсутствие цепочек и циклов.

Требует root-доступа на VPS. Выполняет локальный агент через `scripts/vps-run.ps1`.
